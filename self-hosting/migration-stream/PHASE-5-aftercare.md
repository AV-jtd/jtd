## 5.2 Standby облака

Облачный Supabase оставить в **read-only** минимум **7 дней**:
- Не удалять проект
- Это страховка: при критической проблеме откатываемся на него

После 7 дней стабильной работы — можно понизить тариф/архивировать.

## ПЛАН ОТКАТА

### Сценарий А: откат ДО переключения DNS (Шаг 7 фазы 4)
**Простой: 0.** Просто не продолжаем cutover. Снимаем read-only с облака:
```bash
psql "$CLOUD_DB" -c "ALTER DATABASE postgres SET default_transaction_read_only = off;"
```
Прод как работал на облаке, так и работает. Чиним проблему на staging.

### Сценарий Б: откат ПОСЛЕ переключения DNS
**Простой: ~15 мин (TTL=60с).**

```bash
# 1. Вернуть DNS на старый Supabase-фронтенд / прежний IP
#    justtodoit.ru A <старый IP> TTL=60

# 2. Снять read-only с облачной БД
psql "$CLOUD_DB" -c "ALTER DATABASE postgres SET default_transaction_read_only = off;"

# 3. Если на VPS успели появиться новые данные — перенести их обратно:
./scripts/reverse-delta.sh self-hosting-db-1 "$CLOUD_DB"
```

> Чем быстрее принято решение об откате, тем меньше дельта данных,
> созданных на VPS, которую нужно вернуть в облако. Решение об откате
> принимать в первые часы.

### Сценарий В: частичный откат (только AI или Push)
Если основное работает, но AI Gateway недоступен из РФ:
```bash
# Переключить AI-функции на резервный РФ-провайдер (GigaChat/YandexGPT)
# или OpenRouter. Код функций — переменная окружения AI-эндпоинта.
docker compose ... restart edge-runtime
```
