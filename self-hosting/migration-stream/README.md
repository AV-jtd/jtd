# Стрим: Полный переезд JTD на российский сервер

> Цель: перенести всю инфраструктуру (БД, Auth, Realtime, Storage, Edge Functions,
> фронтенд) из облачного Supabase (AWS) на собственный российский VPS, чтобы
> обеспечить стабильный доступ из России и контроль над данными.

Этот стрим — **отдельный поток работ**, независимый от улучшений архитектуры
(индексы, пулинг и т.д.). Он опирается на уже сделанные кирпичики:
- **п.1 (бэкапы)** — `self-hosting/backup/` используется для миграции данных
- **п.2 (S3 Storage)** — `self-hosting/storage/` используется для переноса файлов

---

## Карта компонентов: откуда и куда

| Компонент | Сейчас (облако) | После переезда (РФ) | Как переносим |
|---|---|---|---|
| PostgreSQL | `*.supabase.co` (AWS) | VPS Selectel/Timeweb | pg_dump → pg_restore |
| Auth (GoTrue) | облако | в стеке на VPS | вместе с БД (таблицы `auth.*`) |
| REST (PostgREST) | облако | в стеке на VPS | код не меняется |
| Realtime | облако | в стеке на VPS | код не меняется |
| Storage (файлы) | облако | РФ S3 (Timeweb/Selectel) | migrate-to-s3.sh (п.2) |
| Edge Functions ×25 | облако | edge-runtime на VPS | код не меняется |
| Cron задания | облако | pg_cron на VPS | migrate-cron.sql |
| Фронтенд | Lovable CDN | nginx на VPS | bun run build → dist/ |
| AI Gateway | Lovable/OpenRouter | тот же внешний API | перенос ключа |
| Push (FCM) | Google | Google (без изменений) | вынесено в отдельный риск |

## Принципы безопасности переезда

1. **Никаких необратимых действий до фазы 4.** Старый облачный Supabase
   остаётся рабочим и нетронутым до самого переключения.
2. **Репетиция обязательна.** Фазы 1–3 — полный прогон на тестовом окружении
   с реальными данными до боевого cutover.
3. **DNS с низким TTL.** За 24 часа до cutover снижаем TTL до 60с, чтобы
   откат через DNS занимал минуты.
4. **Двойной бэкап перед cutover.** Свежий дамп облачной БД + дамп после
   первичной заливки на VPS.
5. **Откат на каждом шаге.** Пока DNS не переключён — откат мгновенный
   (просто не трогаем прод). После — возврат DNS на старый Supabase.

## Оценка простоя

| Сценарий | Простой |
|---|---|
| Идеальный (данные предзалиты, только дельта) | **10–15 мин** |
| Реалистичный (полная заливка при cutover) | **20–40 мин** |
| Окно для проведения | Ночь ВС→ПН по МСК (минимум активности) |

Метод снижения простоя: основной объём данных заливается заранее (фаза 2),
при cutover переносится только **дельта** изменений за период репетиции.

## Реестр рисков

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| AI Gateway недоступен из РФ | Средняя | Среднее | Запасной OpenRouter ключ + резервный РФ-LLM (GigaChat/YandexGPT) |
| FCM Push не работает в РФ | Высокая | Низкое | Telegram-уведомления как основной канал |
| Расхождение данных при дельте | Низкая | Высокое | Сверка row counts (verify-migration.sh) |
| SSL/домен не резолвится | Низкая | Высокое | Заранее выпустить сертификат, проверить на staging-поддомене |
| pg_cron/pg_net не включены | Средняя | Среднее | Проверка расширений в PHASE-0 |
| Realtime WebSocket за nginx | Средняя | Среднее | Проверка проксирования upgrade-заголовков |

## Definition of Done

- [ ] Все данные на VPS, row counts совпадают с облаком (verify-migration.sh = OK)
- [ ] Файлы доступны через S3-бэкенд (test-s3.sh = OK)
- [ ] Пользователи логинятся, задачи открываются, чат работает (smoke-test.sh = OK)
- [ ] Realtime-обновления приходят (ручная проверка в 2 вкладках)
- [ ] Cron-задания пересозданы и выполняются
- [ ] Бэкапы на VPS идут по расписанию (п.1)
- [ ] DNS переключён, старый Supabase в режиме read-only standby 7 дней
- [ ] План отката проверен и задокументирован
