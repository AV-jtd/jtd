
собирает и деплоит на VPS + применяет миграции (deploy-vps.yml).

- Облачный Lovable Supabase **не трогаем** — он остаётся рабочим до и после

## Инцидент: облако Lovable продолжало слать отчёты (2026-07-25, устранён)

Пользователь заметил, что еженедельный отчёт по проекту «Retail Week 2026»
продолжает приходить в Telegram. Проверка облачной БД `nvfioycpwyzwukvokwql`
через Lovable MCP показала: **в облаке остались 5 АКТИВНЫХ cron-задач**, все
бьющие в облачные же edge-функции тем же ботом:

| jobname | schedule |
|---|---|
| auto-baseline-lock-hourly | `0 * * * *` (менял данные!) |
| protocol-buffer-flush | `* * * * *` |
| send-weekly-review-friday | `8 5 * * 5` |
| send-weekly-group-report-friday | `8 5 * * 5` |
| send-weekly-ai-review-friday | `8 5 * * 5` |

Данные в облаке заморожены на ~05.07 → команда получала отчёты, построенные
на устаревших данных, не зная об этом. Плюс `auto-baseline-lock-hourly`
ежечасно менял облачную копию, то есть она уже не была чистым слепком.

**Действие:** все 5 задач сняты (`cron.unschedule`), проверено — `cron.job`
пуст. Облако осталось как архив данных, но больше ничего не шлёт и не меняет.
Определения для отката сохранены ЛОКАЛЬНО (не в git — содержат anon-key
облака), см. scratchpad `cloud-cron-rollback.md`.

**Следствие для бэклога #9:** `email_queue_dispatch()` на VPS всё ещё указывает
на облачный URL — но теперь облако молчит, значит эти вызовы уходят в никуда
гарантированно. Пункт остаётся открытым.

**Осталось проверить:** что VPS-cron реально шлёт еженедельные отчёты
(`SELECT jobname, schedule, active FROM cron.job;` на VPS + `weekly_send_log`
за последнюю пятницу). Если нет — отчётов не будет вообще.

## Правило разработки на будущее

Любые изменения схемы БД — **только через миграции в git**, никогда через
ручной SQL-редактор Lovable. Иначе объект не попадёт в git и не доедет до VPS
(так и появилась проблема с таблицей `clients`). Данные живут только на VPS,
код течёт через git+авто-деплой.
