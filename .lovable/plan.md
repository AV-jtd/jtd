## STM Mission Control — план доработок

Фокус: воркфлоу (логика этапов и риск-сигналы) в первую очередь, UI-навигация во вторую. Реализация поэтапная — каждый этап самодостаточен и проверяем.

---

### Этап 1. Статусы этапов + time-in-stage (приоритет №1)

**Проблема.** Сейчас этап — бинарный чекбокс (`is_completed` true/false). Риск считается только по `deadline`. Для СТМ-конвейера главный сигнал — «этап завис N дней» (ждём образцы, дегустацию, ответ сети), а не формальная просрочка.

**Что делаем:**

1. **Статус этапа.** Добавляем поле `stage_status` в задачу-этап: `pending` (ожидает) / `in_progress` (в работе) / `blocked` (заблокирован) / `done` (готово).
   - `done` остаётся синонимом `is_completed = true` (не ломаем существующую логику и каскады).
   - Клик по ячейке: левый клик — toggle done (как сейчас), доп. меню (правый клик / иконка) — выбор статуса `in_progress` / `blocked`.
   - В компактном режиме статус кодируется цветом/формой точки: серый=pending, синий пульс=in_progress, жёлтый=blocked, зелёный=done, красный=просрочен.

2. **Time-in-stage.** Считаем, сколько дней SKU стоит на текущем этапе:
   - От даты завершения предыдущего этапа (`completed_at` предыдущего) до now; если предыдущего нет — от `start_at` текущего.
   - Порог «застрял»: настраиваемая величина (по умолчанию 7 дней для `in`, 3 для `out`), при превышении — оранжевый бейдж «⏳ 12 дн на этапе».
   - Заблокированный этап (`blocked`) подсвечивается отдельно независимо от дней.

3. **Новый риск-сигнал в `stmRowState`.** Добавляем состояние `stuck` (между `active` и `overdue`): строка получает янтарную полосу-индикатор. Приоритет: archived > overdue > blocked > stuck > done > active > idle.

4. **Дашборд.** Новый KPI «Заблокировано / Зависло» (кол-во SKU со `stuck`/`blocked`), кликабельный фильтр.

**Технически:**
- Миграция: `ALTER TABLE tasks ADD COLUMN stage_status text` (для строк `task_type='stm_stage'`), бэкфил из `is_completed`.
- `stmAnalytics.ts`: функции `timeInStage(project)`, новое состояние `stuck`, метрики `blockedSkus`/`stuckSkus`.
- Хук `useSetStmStageStatus` рядом с `useToggleStmStage` (оптимистичный апдейт через `patchStageTaskInCache`).
- UI: `StmMatrixCell` (цвет точки + статус), `StmExpandedRow` (бейджи time-in-stage и blocked), `StmDashboardBar` (KPI).

---

### Этап 2. Менеджер SKU: показ и фильтр

**Проблема.** `manager_id` лежит в `stm_meta`, но не виден в матрице и по нему нельзя фильтровать. Менеджер не видит «свои» SKU.

**Что делаем:**
- Аватар/инициалы менеджера в строке SKU (рядом с именем) — переиспользуем профили из `StmExpandedRow`.
- Фильтр в топ-баре: «Менеджер» (мультиселект) + быстрый тумблер «Мои SKU».
- Кликабельная метрика менеджеров в дашборде (как «Топ сетей»).

---

### Этап 3. Сортировка + расширенные фильтры

**Проблема.** Сейчас только группировка; нельзя сортировать и фильтровать по риску.

**Что делаем:**
- Сортировка списка: по прогрессу / по просрочке (дни) / по дедлайну / по time-in-stage / по имени. Селектор рядом с «Группировка».
- Фильтры-тумблеры: «Только просроченные», «Зависшие/заблокированные», «К запуску» (approval done, прогресс <100).
- Мультиселект по сети (сейчас группировка + поиск-строка делают это частично).
- Все фильтры синхронизируются с URL (как `sku`/`stage`) для шаринга ссылок.

---

### Этап 4. Bulk-операции

**Проблема.** Нет массовых действий — каждое SKU обрабатывается по одному.

**Что делаем:**
- Режим выбора (чекбоксы на строках), панель действий снизу.
- Действия: массовый сдвиг дедлайнов (с каскадом), назначить менеджера, перевести в архив с общим комментарием, переключить flow.
- Переиспользуем паттерн каскада из `useShiftStmStageDate`.

---

### Порядок и проверка

1. Этап 1 (миграция + логика + UI статусов) — ядро, делаем первым.
2. Этап 2 (менеджер) — лёгкий, быстрый выигрыш.
3. Этап 3 (сортировка/фильтры) — UX-навигация.
4. Этап 4 (bulk) — самый объёмный, в конце.

Каждый этап проверяется в превью на матрице STM (`/npd/stm`): создание/тоггл этапа, отображение бейджей, фильтрация, отсутствие регрессий в каскадах и Gantt.

### Технические заметки
- Поля статуса добавляются только к `task_type='stm_stage'`, глобальные списки задач их игнорируют (как сейчас).
- `done`/`is_completed` остаются единственным источником для прогресса и каскадов — `stage_status` это надстройка, а не замена.
- Виртуализация: новые бейджи не меняют высоту строки в компактном режиме (точки), в комфортном — учитываем в `estimateSize`.
