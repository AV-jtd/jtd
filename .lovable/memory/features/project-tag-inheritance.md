## Авто-связь имени проекта с тегом
При создании проекта (`addGroup` в `useTasks.tsx`):
1. Ищется свободный (не привязанный ни к какому проекту через `linked_tag_id`) тег с тем же именем (case-insensitive, в рамках `user_id`).
2. Если найден — переиспользуется как `task_groups.linked_tag_id` (зеркало). Все задачи, ранее помеченные этим тегом, автоматически попадают под зонтик нового проекта при фильтрации (см. `mem://features/project-hierarchy-filtering`).
3. Если не найден — создаётся новый тег с именем проекта.
4. Если все одноимённые теги уже linked к другим проектам — нарушение `unique-naming-policy`, выбрасывается ошибка через `checkDuplicateName`.

## Наследование контекстных тегов (group_tags) подпроектами
При создании подпроекта (`parent_id != null`):
- ВСЕ `group_tags` родителя копируются в `group_tags` нового подпроекта (включая системные оси: площадка/бренд/территория).
- Это даёт подпроекту сразу полный контекст родителя; пользователь может снять лишние теги вручную.
- `linked_tag_id` сам в `group_tags` не дублируется (он и так зонтик).

## Параметр initial_tag_ids
`addGroup` принимает опциональный `initial_tag_ids: string[]` для случаев, когда вызывающий код хочет сразу навесить контекстные метки (например, создание проекта из триаж-экрана с уже выбранной площадкой/брендом). Системные vs не-системные не различаются на этом уровне — ответственность вызывающего.

## Что НЕ делается автоматически
- Системные теги контекста (9 категорий из `mem://streams/context-model`) НЕ навешиваются магически на проект верхнего уровня — только через явный `initial_tag_ids` или ручной выбор в UI после создания.
- Нет диалога «связать как зеркало или как метку?» при коллизии имени — поведение детерминировано (зеркало, если тег свободен; ошибка, если занят).
