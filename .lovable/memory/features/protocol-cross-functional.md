Шаблон протокола `cross_functional` — это внутренний регулярный ритуал команды (в отличие от `client_negotiation`/«переговоры», который служит базой). Доработки:

1. **Форма создания (NewProtocolDialog)**:
   - Скрыты партнёрские axes-чипы (required_axes/optional_axes) — для внутренней встречи это шум.
   - Описание не подставляется автоматически (для других шаблонов оставлено как было).
   - Блок «Подтянуть открытые поручения с прошлых встреч»: подгружает последние до 10 cross_functional протоколов владельца (по `protocol_meta.template_system_key` или префиксу имени) с агрегированным счётчиком незакрытых задач. Пользователь чекбоксами выбирает **несколько** прошлых протоколов; при создании в новый протокол клонируются все их `is_completed=false` задачи как `is_draft=true`. На каждой клонированной задаче сохраняется `source_protocol_id` = id оригинального протокола, что даёт корректную трассировку при переносе из нескольких источников. По умолчанию авто-выбирается самый свежий протокол с открытыми задачами; протоколы без открытых задач — disabled.
   - При создании в `protocol_meta` пишется `template_system_key` для надёжной идентификации в будущем.

2. **Soft-дисциплина (ProtocolDetailPage)**: для draft cross_functional показывается мягкий баннер (синий/primary, не блокирующий публикацию), если: пустое описание (нет цели встречи) или нет ни одного internal-attendee (ни в `protocol_meta.internal_attendees`, ни среди assignee задач). Это согласовано как «Soft» режим — создаём всегда, баннер информирует.

Поля «модератор/секретарь/чек-лист функций» в этой итерации НЕ добавляли — Артём явно выбрал из ключевых полей только carry-over.
