# Контекстная модель — единый стрим

Объединяет три ранее разрозненных стрима:
- R7 Протоколы совещаний
- Триаж (разбор Inbox)
- Управление тегами/категориями

## Ключевая концепция: двойной срез

Одна задача — два способа смотреть:
- **Временной срез** = протокол/встреча. «Что обсудили 18 апреля». Контейнер: `task_groups` (project_type='protocol').
- **Осевой срез** = по площадке/бренду/проекту/категории. «Все задачи по Купатам на ФЗ». Контейнер: фильтр по тегам.

Задача (`tasks`) одновременно имеет:
- `group_id` — родной проект ИЛИ протокол
- набор `task_tags` по разным осям
- `source_protocol_id` — обратная ссылка на встречу-источник (NULL для не-протокольных задач)

## Блок A — Системные оси (выполнено в миграции 18.04.2026)

`tag_categories.is_system boolean`, `system_key text` (UNIQUE per user), `icon text`.
9 системных категорий, защищены от удаления триггером `protect_system_tag_categories`:

| system_key | Название | Иконка |
|---|---|---|
| `clients` | Клиенты (Пятёрочка, Магнит, Монетка…) | 🏪 |
| `territory` | Территория (Киров, Федерал, Волга) | 🌍 |
| `site` | Площадка / БЕ (АА, ФЗ, КМ, Молоко) | 🏭 |
| `brand` | Бренды | 🏷️ |
| `product_category` | Категории продукта (купаты, сосиски, каши) — **плоская, не зависит от площадки** | 📦 |
| `product_state` | Состояние продукта (охл/зам) | ❄️ |
| `department` | Отделы (R&D, Продукты, Дизайн, Маркетинг, Продажи) | 👥 |
| `event_topic` | События / Темы (Retail Week, качество) | 📅 |
| `stm` | СТМ (плоский ярлык) | ⭐ |
| `contractors` | Контрагенты (подрядчики, внешние поставщики; CRM-карточки в будущем) | 🤝 |

Сидер: `seed_system_tag_categories(_user_id)`. Хук в `handle_new_user()` для новых юзеров. Проход по `auth.users` в миграции — для существующих.

**Важно**: «Проект» НЕ системная ось — это `task_groups`. Темы/события (Retail Week, качество) — это `event_topic` теги, не проекты. Долгоиграющие инициативы (Гриль Огонь) — проекты.

## Блок B — Связь протокол ↔ задача ↔ проект (выполнено в той же миграции)

`tasks.source_protocol_id uuid REFERENCES task_groups(id) ON DELETE SET NULL`.
Триггер `validate_source_protocol` гарантирует, что ссылка указывает на проект с `project_type='protocol'`.

Это даёт два представления:
- В **протоколе** видим строки этой встречи (через `group_id` ИЛИ через `source_protocol_id`).
- В **проекте** появляется секция «📋 Поручения из встреч» — задачи где `group_id = проект` И `source_protocol_id IS NOT NULL`, сгруппированные по дате встречи.
- В триаже: меняем `group_id` (раскладываем в правильный проект), но сохраняем `source_protocol_id` для traceability.

## Решённые архитектурные вопросы

1. **Купаты НЕ дочерние ФЗ** — категории продукта плоские, могут пересекаться по площадкам. Используем AND-фильтрацию по нескольким независимым осям.
2. **Проект vs Событие/Тема — раздельно**: Проект = `task_groups` (имеет задачи/чат/wiki), Событие/Тема = тег `event_topic` (для группировки задач из разных проектов).
3. **СТМ = один тег**, не категория с подтегами.
4. **Отделы** могут получить связь «отдел → ответственный по умолчанию» в будущей итерации.

## Что осталось (UI постепенно)

- UI управления системными категориями (нельзя удалить, можно редактировать состав тегов).
- Шаблоны протокола используют системные оси (`site`, `event_topic`, `clients`) автоматически вместо ручного создания.
- Секция «Из протоколов» в детальной панели проекта.
- Колонка «→ Проект исполнения» в Table View протокола.
- Триаж-экран (после того как Артём вернётся с моделью контекста) — будет переиспользовать те же оси.
