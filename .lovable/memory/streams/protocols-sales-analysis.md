# Протоколы продаж — нужен ли отдельный стрим?

## Что сделали сегодня (один тип = «протокол переговоров с клиентом»)
- Парсинг сторон встречи из названия (`partner x ours`).
- Карточки сторон в шапке + 3 слота логотипов (наша сторона, партнёр, иконка протокола).
- Авто-привязка партнёра к CRM-клиенту + диалог быстрого создания клиента.
- Расширенный AssigneePicker: компании партнёра, контактные лица партнёра (из external_attendees + CRM contact), наши пользователи. Назначение «на компанию» как сущность.
- Тумблер «Имена / Стороны» в превью (PDF / Email / Telegram) — анонимизация перед отправкой партнёру.
- Двухконтурная модель: внешние строки идут партнёру, внутренние (`protocol_scope='internal'`) и внутренний контекст внешней строки (`status_meta.linked_*`) — нет.
- Тема как проект (auto-link темы встречи к одноимённому проекту).
- Черновик → публикация, soft-review для секретаря и ответственных, мобильная адаптация.

## Тезис: нужен ли отдельный стрим «Sales Protocols»?

**Мой ответ: нет, отдельный стрим выделять рано.** Вот почему.

### Что сделали — это не «продажный» функционал, а универсальная B2B-механика
Все сегодняшние фичи одинаково применимы к 4 кейсам:
1. **Переговоры с клиентом** (Лента x Дороничи) — продажа.
2. **Переговоры с поставщиком** (Дороничи x Ивановский комбинат) — закупка.
3. **Совет директоров / партнёрское СП** (две стороны, обе «наши»).
4. **Кросс-функциональный проект с подрядчиком** (RnD + внешнее агентство).

Во всех четырёх работают: парсинг сторон, логотипы, AssigneePicker с компаниями партнёра, анонимизация в превью, двухконтурная модель «что уходит / что не уходит партнёру». Слово «продажа» нигде в коде не зашито — только концепция «партнёр vs наша сторона».

### Шаблон `client_negotiation` — это вход, а не отдельный продукт
В `protocol_templates` уже есть system_key `client_negotiation` (Этап 4 R7). Все остальные системные шаблоны (`npd_gate`, `cross_functional`, etc.) используют тот же движок. Отделять «продажный» в свой стрим = плодить дублирующую инфраструктуру.

### CRM-связка уже встроена в общий протокол
- `protocol_meta.client_id` → CRM-карточка.
- Задачи протокола наследуют `client_id` → попадают в CRM-доску.
- AssigneePicker уже знает о контакте CRM-клиента.
Это и есть «продажный режим» — он включается фактом привязки клиента, а не отдельным типом протокола.

## Что **действительно** имеет смысл доработать (но в рамках R7, не отдельный стрим)

Если со стороны бизнеса есть запрос «улучшить продажные протоколы» — это поштучные доработки, не новая платформа:

1. **Связь со стадией CRM-воронки**.
   Сейчас: задачи протокола падают в воронку клиента. Не хватает: явного указания «это встреча на стадии X», авто-двиг клиента на следующий этап после публикации протокола, чек-листа «обязательные исходы встречи на этой стадии».

2. **История встреч с клиентом в CRM-карточке**.
   Сейчас протокол → клиент односторонний. В CRM-карточке клиента нужен таб «Встречи» с тайм-лайном протоколов (последняя дата, ответственные с двух сторон, ключевые решения).

3. **Шаблоны исходов переговоров** (categorical closure).
   Сейчас `closure_result` свободный текст. Для продаж полезно: «договорились / отложили / отказ / нужна доработка» как enum + auto-rollup в воронку и weekly review.

4. **Коммерческие приложения** (КП, прайс, NDA).
   `closure_attachments` есть, но нет тегирования «КП v2», версионирования и связки «отправили КП → дедлайн ответа». Это фича привычная только для sales — её можно вырастить в `closure_attachments_meta`.

5. **Email-резюме партнёру с CTA-блоком**.
   Сейчас «Имена/Стороны» + текстовое резюме. Для sales: блок «Дальнейшие шаги: ждём от вас X к дате Y» + кнопка «Подтвердить» в письме (web-link на public preview с подтверждением).

6. **Метрика «средний срок исполнения договорённостей по клиенту»** в CRM Risk Radar — сейчас протоколов нет в Radar.

## Решение
- **Не создавать отдельный стрим «Sales Protocols»**. Текущий R7 + `protocol-partner-side` достаточно покрывают B2B-кейс.
- Пункты 1–6 выше — кандидаты в backlog для **Этапа 7 R7** под зонтиком «CRM ↔ Protocol интеграция». Бизнес-приоритет ставит Артём.
- Если в будущем появится сильно отличающийся домен (например, **внутренние HR/IDP-протоколы**, где нет понятия «партнёр»), тогда выносить отдельный стрим.

## Почему сегодня было сложно (ретроспектива одного типа)
Затраты времени ушли не на «продажную специфику», а на:
- Пересборку шапки (карточки сторон vs прежние блоки участников).
- Двухконтурную модель — это новая концепция, требует осторожной RLS/триггер-инвариантности (видимость linked-задач в NPD/PMO/CRM).
- Мобильную адаптацию + публичную версию + анонимизацию (3 разных рендера одной таблицы).
- Поток черновика и soft-review задач (триггер + автозакрытие).

Это инфраструктура для всех типов протоколов разом. Под второй и третий тип (NPD-gate review, internal cross-functional) останется только подменить шаблон и набор системных колонок — основной движок переиспользуем.
